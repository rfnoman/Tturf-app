## Phase 02 additions

| ID | Question | Decision | Affects |
|---|---|---|---|
| D24 | Maps | **Leaflet + OpenStreetMap tiles**, as the phase file proposed. Free, no API key, no per-load billing, and the OSM data for Dhaka is good enough to place a turf. Driven through Leaflet's imperative API rather than react-leaflet so the map is one client boundary with no extra wrapper library. Switching to Google Maps later means replacing one component. **Leaflet reads `window` at module scope**, which `"use client"` does not prevent — Next still evaluates client modules on the server for the initial HTML — so it is loaded through `next/dynamic` with `ssr: false` in `components/turf/turf-map.tsx`; importing the implementation directly is a 500. Its default marker PNG is resolved relative to Leaflet's own CSS and no bundler rewrites it, so markers are an inline-SVG `divIcon`. | Phase 02+ |
| D25 | How do Phase 03 bookings reach the availability selector? | **A provider registry** in `apps/turfs/availability.py`. `apps.turfs` must not import `apps.bookings` (the dependency runs the other way), so availability asks a list of registered callables for the ranges already taken; Phase 03's `AppConfig.ready()` registers one. Until then the list is empty and every open slot reads as free. Satisfies the phase brief's "write the selector so it already queries them via an interface" without a circular import or a rewrite later. | Phase 02, 03 |
| D26 | Which slot does a price rule apply to? | **The band the slot *starts* in.** A 90-minute booking that straddles the peak boundary keeps the price it was quoted; repricing halfway through would make the displayed price a lie. Where several rules match, the **most specific wins**: fewer weekdays beats more, then a shorter window beats a longer one — so a turf keeps one broad "all week" rule and overrides Friday nights without reordering anything. | Phase 02, 03 |
| D27 | Turfs that close after midnight | **`close_time <= open_time` means the window crosses midnight**, and equal times mean a full 24 hours. 18:00–02:00 is a normal Dhaka evening, so availability for a date includes both that date's own window *and* the tail of the previous day's. Price coverage follows the same rule, which is why the 00:00–02:00 tail needs a price on the **following** weekday. | Phase 02, 03 |
| D28 | Who sees a ground that is not bookable? | **Owners and reviewing admins, never players.** A ground is created inactive and only becomes bookable once its open hours are fully priced, so hiding inactive grounds from the owner would hide the exact row they have to price and activate. The public selector still filters them out. (Found in Phase 02 by driving the owner flow in a browser; the API tests had only ever built active grounds.) | Phase 02+ |

## Phase 03 additions

| ID | Question | Decision | Affects |
|---|---|---|---|
| D29 | Preventing double bookings | **A Postgres `ExclusionConstraint`**, not an application check. Two requests racing for the same slot both pass any `SELECT … WHERE overlaps`; only the database can break the tie. `ground WITH =, time_range WITH &&`, restricted to the statuses that actually hold a slot, so cancelling frees it at once. `create_booking` catches the `IntegrityError` and raises `SlotTakenError`, which the API returns as **409** — nothing the client sent was wrong, somebody was simply faster. Needs `btree_gist` (uuid has no default GiST operator class), which the bookings migration now depends on explicitly. | Phase 03+ |
| D30 | Where a payment points | **Two nullable FKs (`booking`, and `order` from Phase 08) with a check constraint**, not a `GenericForeignKey`. Generic relations would cost referential integrity and join-ability and buy nothing: there are exactly two targets, and Phase 10's ledger has to join both. | Phase 03, 08, 10 |
| D31 | Notification content | **Rendered once, at creation**, from a template table in `apps/notifications/templates.py`. A notification is a record of what the player was *told at the time*; re-rendering later from live data would silently rewrite history when a booking is cancelled or repriced. A test asserts every `NotificationKind` has a template, and `notify` never raises — a missing placeholder must not roll back the booking transition that triggered it. | Phase 03+ |
| D32 | Late cancellation by the turf | **Does not count against the player.** DOMAIN §5 penalises late cancellations, but the rule exists to discourage players from stranding a turf — not to punish them when the venue floods. `cancel_booking(by_staff=True)` skips the reliability hit. | Phase 03, 06 |
| D33 | Who a walk-in booking belongs to | **The staff member's account**, with the customer's name and phone on the booking. There is no account to attach it to, and the cashier is the right person to receive its notifications — they are the one who has to tell the customer. Visibility is forced to `private`: a counter booking is not looking for players. | Phase 03, 04 |
| D34 | Enum names in the generated schema | **Explicit `ENUM_NAME_OVERRIDES`.** Several apps have a `status` field with different choices, and drf-spectacular otherwise mints names like `Status4eaEnum` that change whenever another `status` field is added anywhere — churning the generated TypeScript on unrelated edits. Nested `TextChoices` cannot be reached by a dotted path, so each model exposes a module-level `*_CHOICES` alias. | All phases |

## Phase 04 additions

| ID | Question | Decision | Affects |
|---|---|---|---|
| D35 | How does a booking get a match? | **A hook registry on the booking lifecycle**, the same pattern as Phase 02's availability (D25). `Match` holds the FK to `Booking`, so `apps.bookings` must not import `apps.matches`; instead it fires `booking_created` and `booking_transitioned`, and `MatchesConfig.ready()` subscribes. The create hook runs **inside** the booking transaction on purpose — a booking with no match is not a state the rest of the app knows how to handle, so a failure there should roll the booking back. | Phase 03, 04+ |
| D36 | Match visibility | **Derived on creation from the booking and the squad, never set by hand** (DOMAIN §6): individual+public and group+open become `board`; individual+private becomes `private`; group+closed becomes `squad`. Storing it as an independent field would let it drift from the booking the first time one is edited. The *organiser* is derived the same way — squad leader, else booker. | Phase 04+ |
| D37 | Capacity under contention | **`select_for_update` on the match, counted inside the lock.** Two approvals for the last spot must not both succeed, and no amount of `if match.is_full` before the write prevents that. The losing request stays `pending` rather than being auto-declined, so the organiser sees why nothing happened instead of a request vanishing. | Phase 04+ |
| D38 | The board's average rating | **A correlated subquery**, not a join. Joining `PlayerSportRating` multiplies the roster rows and silently corrupts the `spots_left` count computed alongside it. A match whose roster is entirely unrated stays **visible** under a rating filter — a brand-new player's match is exactly what somebody browsing the board wants to find, and hiding it would make the app useless to the people it most needs. | Phase 04, 06 |
| D39 | Naming a player in an API request | **By `PlayerProfile` id**, never the account id. The account id is not exposed anywhere in the API, and the profile id is what every card, roster row and search result already carries. | Phase 04+ |
| D40 | Validating a scorecard across sports | **A registry keyed by sport slug, with a generic pass that always runs first.** The generic validator enforces the bounds declared on each `StatDefinition` and that every player given a stat was on the roster; the sport-specific one then adds what only that sport knows (goals ≤ score, cricket totals reconciling, no drawn badminton match). A sport with no registered validator is therefore still validated, which is what makes adding a sport a catalogue row rather than a code change. Issues come back **grouped by field**, so the entry form can put each message against its own input instead of showing one wall of text. | Phase 05+ |
| D41 | Who confirms a scorecard | **The captain of the side the scorer did not play on.** DOMAIN §7 says "the opposing captain", which only means something once we can say which side the scorer was on — so it is resolved from the scorer's own team sheet. When the scorer did not play (turf staff), **either** captain may confirm. Turf staff may always confirm, and a card they enter is `verified_by_staff` from the outset (D7). | Phase 05+ |
| D42 | Saving a draft scorecard | **Drafts are stored unvalidated.** A scorer standing at the side of a pitch on a phone fills the card in the order the match happened, not in the order that keeps it internally consistent; refusing a save halfway would lose what they had typed. Validation happens once, at **submit**. | Phase 05+ |
| D43 | What a locked card shows the world | **Only locked cards have a public page**, and the public serializer drops every reader-relative field (`can_*`, votes, the dispute reason and the event history). A card still being argued over is not a result, and the link is meant to be pasted into a group chat. | Phase 05, 11 |
| D44 | Who owns a player's overall rating | **The self-assessment until they play, the engine from then on.** `refresh_sport_rating` stops writing `overall` once `matches_counted > 0`. Before this, editing a skill slider on the settings page silently undid every match a player had earned — the Phase 01 formula recomputed the overall from the sliders and wrote it back. The sliders still move their skills; they no longer move the number that was earned. | Phase 06+ |
| D45 | How a rating is recomputed from history | **By replaying the stored inputs, not by re-reading the matches.** Every `RatingChange` carries the match exactly as the engine saw it — stats, result, MOTM, peer average and both team averages. A replay re-runs those, so it lands on precisely the numbers the incremental updates produced. Re-deriving the team averages at replay time would mean a teammate improving next month quietly rewrote your history, and a "deterministic, recomputable" engine that gives a different answer each time it is run is worth nothing. | Phase 06+ |
| D46 | What the rating engine refuses to guess | **A skill no stat speaks to is left exactly where it is, and only stamina moves among the shared attributes.** Nudging dribbling towards the overall because somebody scored would make "why did my dribbling change?" unanswerable, and inventing speed from goals would be worse than leaving a self-assessment alone. Weights live in one versioned table (`WEIGHTS_VERSION`) so the numbers can be tuned without touching the arithmetic, and so a stored explanation stays true to the weights it was made with. | Phase 06+ |
| D47 | When a conduct report counts | **Only once an admin upholds it.** An accusation is not evidence, and a fair-play score anybody can move by complaining is worthless. Open reports are visible to the admin queue alone; the score is built from cards recorded on locked scorecards and upheld reports, nothing else. | Phase 06+ |
| D48 | How stock quantities change | **Only through a service, under `select_for_update`, alongside the `StockMovement` that explains it.** `StockItem.on_hand` and `reserved` are a cache of the ledger; the ledger is the record. Views, serializers and the Django admin never write them, the movement table is append-only (a correction is another movement), and a test replays every movement against the cached columns. Without this, "where did my 30 waters go?" has no answer and a race has no witness. | Phase 07+ |
| D49 | What "reserved" means for rented gear | **Rented gear stays `on_hand` and becomes `reserved`.** It is still the turf's property and it is coming back, so removing it from stock would misreport what the turf owns; but it cannot be handed to a second team, which is exactly what `reserved` expresses. Gear that is never returned leaves stock through an adjustment, with the deposit kept. | Phase 07+ |
| D50 | Out of stock is a 409 | **Not a 400.** The request was well-formed; the shelf changed under it. The distinction matters at the counter, where a cashier needs "somebody just took the last one" rather than "your request was invalid", and in the Phase 08 store, where a 409 means "re-read availability and try again". | Phase 07, 08 |
| D51 | A refused fulfilment option still appears | **Closed options are shown with the reason they are closed, never hidden.** "Delivery is missing" reads as a broken app; "orders have to be in 16 hours before kick-off" reads as a rule, and the player orders earlier next time. The reason is part of the API's answer, not copy invented by the client, so there is one place to change it. | Phase 08+ |
| D52 | Checkout is all or nothing | **One transaction across every order a cart splits into.** If the last line of the second order is gone, the first is rolled back and the cart is left untouched. A player told "ordered" who receives half of it has been lied to, and a half-reserved shelf is worse than a refusal. | Phase 08+ |
| D53 | A payment belongs to exactly one thing | **`Payment` targets a booking or an order, never both and never neither**, enforced by a check constraint. Phase 03 anticipated it; Phase 08 added the column. Without it a row could be counted twice and neither total would be trustworthy. | Phase 08, 10 |
| D54 | Real-time in-app updates: SSE, not Channels | **Server-sent events.** Everything the app pushes — notifications, a join request arriving, a live score — travels server→client; nothing needs a socket back, because every action already goes through REST. SSE therefore buys the same result for far less: no channel layer, no consumers, no second protocol through the proxy, and `EventSource`-style reconnection handled by the browser. Channels would be the right answer the day two clients have to talk to each other (a live chat), and is a contained change if that day comes. **Cost accepted:** a long-lived response holds a worker, so the stream is served by ASGI (`gunicorn -k uvicorn.workers.UvicornWorker`) and the client falls back to the existing polling if the stream will not open. The token travels in a header via `fetch`-streaming rather than in the URL, because a query-string token ends up in every access log. | Phase 09+ |
| D55 | Web push needs one new dependency | **`pywebpush`.** Encrypting a payload for the Web Push protocol is ECDH + HKDF + AES-GCM against a VAPID-signed JWT; hand-rolling that is a security mistake, not an exercise. Push is opt-in per type, stored per device subscription, and silently skipped when `VAPID_PRIVATE_KEY` is unset — so development and CI need no keys (CLAUDE.md asks for new libraries to be justified here). | Phase 09+ |
| D56 | A fitness week starts on Saturday | **Dhaka-local, Saturday to Friday.** Bangladesh's weekend is Friday and Saturday, so a player's "this week" means the run that starts the morning after their weekend begins. ISO weeks (Mon–Sun) would cut a Friday-night match off from the Saturday-morning one that belongs with it. The day is a constant (`FITNESS_WEEK_STARTS_ON`), and every boundary test is written in Dhaka time. | Phase 09+ |
| D57 | Only the gateway's own validation API is believed | **Every online payment is settled from a server-to-server validation call, never from the browser's return.** The redirect carries whatever the browser was handed, and a redirect URL is something anybody can type. `SSLCommerzProvider.validate()` therefore makes three checks against SSLCommerz's `validationserverAPI.php` reply and refuses on any one of them: the status must be `VALID` or `VALIDATED`, the `tran_id` must be the one we stored on the payment, and the amount must match to the paisa. A forged or replayed callback fails the second or third check even when it passes the first. The return page and the IPN both run the same `settle_payment`, which returns early if the payment is already `PAID` — so a duplicate IPN, a refreshed return page and both arriving at once all land on one settlement. | Phase 10+ |
| D58 | An unbalanced ledger event cannot be written | **`post_entries()` raises before it writes if the lines of one event do not sum to zero.** It is not a reporting check that runs later; nothing can enter the ledger unbalanced in the first place. Entries are signed (positive is money arriving) and grouped by an `event_id`, so "the ৳1000 booking" is one event of three lines — player −1000, turf +900, platform +100. `unbalanced_events()` exists for an auditor to confirm the invariant held, and a test asserts it is empty across the whole database. A finance screen that cannot be reconciled is worse than no finance screen. | Phase 10+ |
| D59 | What a gateway reply may be stored as | **Stripped before it is saved.** `raw_response` is kept for reconciliation and disputes, so `_safe()` removes `store_id`, `store_passwd`, `card_no`, `verify_sign` and `verify_key` on the way in: card numbers and our own credentials have no business in a database row, a log line or an error report, and the one way to be sure is never to put them there. The player-facing serializer drops `raw_response` entirely — the gateway's reply is for reconciliation, not for the browser. | Phase 10+ |
| D60 | An advance overrides the track-record rule | **A paid advance confirms the booking, even for a player D3 would have held.** D3 holds a new player's booking because nothing yet says they will turn up; money in hand says it better than a track record does. The advance percentage is a turf setting (`Turf.advance_percent`), because a turf in Gulshan and one in Mirpur do not have the same no-show problem. The balance is then payable in cash at the counter or online, and `mark_paid(record_payment=False)` keeps the counter from recording a second cash payment for money that already arrived through the gateway. | Phase 10+ |
| D61 | Payouts are drafted by the system and sent by a human | **The statement is computed from the ledger; the transfer is manual and recorded back.** There is no disbursement API here — an admin reads the statement, moves the money by bank or bKash, and marks the payout sent with its reference. The payout is itself a ledger event, which is what drives a paid-out turf's balance to zero rather than leaving the earnings to be counted again in the next period. Automating the transfer is a contained change behind the same two service functions when a payout API is worth the integration. | Phase 10+ |
| D62 | Bangla uses Western digits | **Bangla words, `0123` numbers.** `Intl` renders `bn` with Bengali numerals (০১২৩) by default, and Phase 11 deliberately turns that off: bKash, Nagad, Pathao and Daraz all write Bangla prose with Western digits, so that is what these players read money and times in every day. A price is the one thing in the app nobody should have to read twice. It is one constant (`NUMERALS` in `src/i18n/formats.ts`) and switching it to `"beng"` changes the whole app, which is what makes it an option rather than a decision baked into 38 call sites. English formats as **en-GB**, not bare `en` — `Intl` reads bare `en` as American and gives 12-hour clocks and month-before-day, which is not how Bangladesh writes either. | Phase 11+ |
| D63 | Which database text is translated | **Generic nouns are; proper nouns are not.** Sports, product categories, player attributes, per-sport skills, scorecard stat definitions and format names each carry a `*_bn` column, resolved per request from `Accept-Language` (which the frontend sets from its locale cookie) by `in_readers_language`. Turf names, player names, squad names and product brands are left exactly as written: "Dhanmondi Arena" is not translated by anyone in Dhaka, and a store that renamed somebody's brand would be wrong rather than localised. A blank `*_bn` falls back to English rather than raising, because a sport an admin approved five minutes ago has no Bangla name yet and showing its English one is the right answer. The alternative — shipping both names to the browser and choosing there — would have put the choice in every one of the forty-odd places a label is rendered. | Phase 11+ |

### D9 — phone sign-in for Bangladesh (+880)

Resolved from Clerk's current documentation. What is **confirmed**:

- Clerk's SMS allowlist enables **only the US and Canada by default**. A disabled country
  cannot receive OTPs *or be used at sign-up at all* — so with +880 off, Bangladeshi phone
  sign-up is fully blocked, not merely degraded. Toggle: Dashboard → SMS → Settings.
- **Phone authentication requires a paid plan in production** (development instances can
  test it free).
- Countries sit in tiers A–F gated on a `phone_code` plan feature. Removing a tier B–F
  country from the blocklist on a free/dev instance fails with
  `SMSCountryRemovalRestricted`, "to prevent SMS pumping abuse".
- No current Clerk documentation offers a bring-your-own-Twilio escape hatch.

What is **not published**: which tier +880 is in, and the per-message cost for Bangladesh
("international at market rate"). Tier A appears to be the default-enabled US/CA set, so
+880 is very likely tier B–F and therefore plan-gated — likely, but unverified.

**Decision:** v1 uses email + Google sign-in, with `phone` as an unverified field on the
profile. Follow-ups before any SMS commitment: (1) try toggling Bangladesh on a dev
instance and see whether it is plan-blocked, (2) ask Clerk support in writing for the
+880 tier and per-message rate.
